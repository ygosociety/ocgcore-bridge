# ocgcore-bridge

A bridge to [edo9300/ygopro-core](https://github.com/edo9300/ygopro-core), the Yu-Gi-Oh! rules
engine behind EDOPro: run duels from any language, over newline-delimited JSON on stdin/stdout.

- **core/**: `libocgbridge`, a C++17 library over ygopro-core. A duel session (decks, a board or an
  EDOPro-style puzzle script, seed, LP, rules), card data from BabelCDB `.cdb` databases or a
  YGOPRODeck-style JSON list, every `MSG_SELECT_*` prompt decoded to JSON and answers encoded back,
  an auto-responder for the prompts inside effects, field snapshots, event queues and decoded
  engine messages.
- **server/**: `ocgcore-bridge`, one duel per process, [protocol v1](docs/protocol.md). Forks copy a
  running duel into a new session, for search. Also a library, for a server with extensions of
  your own.
- **client-ts/**: the `ocgcore-bridge` npm package: spawns the binary, typed protocol, Promise API
  (Node.js 18+).
- **examples/**: a duel between two `.ydk` deck lists with random players, a puzzle (JSON board and
  EDOPro Lua script), a fork-based search, a server with C++ extensions.

Your own rules go on top, through extension points rather than a fork of this code
([docs/extending.md](docs/extending.md)): an ask hook that answers or inspects any prompt, a
pluggable auto-responder (manual kinds, replacement default answers), message filters (subscribe
to or drop engine messages) and named queries.

ocgcore-bridge is not affiliated with or endorsed by Project Ignis, the EDOPro team or Konami.
Engine bugs (a card that resolves wrongly) belong upstream: ygopro-core for the engine,
CardScripts for a card's script.

## Build

CMake 3.16+, a C++17 compiler, git, and optionally SQLite 3 (for `.cdb` databases).

```bash
cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
./build/ocgcore-bridge --version
```

ygopro-core and nlohmann/json are fetched at pinned commits. On Debian / Ubuntu:
`apt install cmake g++ git libsqlite3-dev`. On macOS, SQLite comes with the system.

## Card data

The engine needs two things at run time:

- the card scripts: [ProjectIgnis/CardScripts](https://github.com/ProjectIgnis/CardScripts)
  (`--scripts DIR`);
- the card data: [ProjectIgnis/BabelCDB](https://github.com/ProjectIgnis/BabelCDB) databases
  (`--cdb cards.cdb`, repeatable), or a YGOPRODeck-style JSON card list (`--cards-json`, with the
  setcodes supplement in `data/setcodes.json`, generated by `tools/gen_setcodes.py`).

`tests/golden/fetch-data.sh` fetches both at the commits the tests are pinned to
(`tests/golden/pins.json`) into `tests/data/`.

## A duel over stdin/stdout

```bash
./build/ocgcore-bridge --scripts tests/data/CardScripts --cdb tests/data/BabelCDB/cards.cdb
```

```json
{"type":"ready","protocol":1,"version":"0.1.1"}
{"id":1,"type":"init","seed":42,"players":[{"main":[89631139,55144522,5318639,…]},{"main":[46986414,83764718,12580477,…]}]}
{"id":1,"ok":true,"result":{"state":{"duel":"active","pending":{"kind":"idle","player":0,"activatable":[…],"toEnd":true,…},"turn":1,…}}}
{"id":2,"type":"respond","answer":{"action":"activate","index":0}}
{"id":2,"ok":true,"result":{"answered":[],"state":{…},"status":"none"}}
```

Every prompt arrives as JSON in `state.pending` (its `kind`: `idle`, `battle`, `chain`, `card`,
`place`, `position`, ...); answer it with `respond`. Prompts inside an effect (where to place a
monster, which card to add...) are answered by the auto-responder unless you ask for them
(`init.responder.ask`) or hold them (`hints.hold`). See [docs/protocol.md](docs/protocol.md) for
every message.

## From Node.js

```ts
import { Bridge } from 'ocgcore-bridge';

const bridge = await Bridge.start({ binary: './build/ocgcore-bridge', scripts: 'CardScripts', cdb: ['cards.cdb'] });
let state = await bridge.init({ seed: 1, players: [{ main: deckA, extra: extraA }, { main: deckB }] });
while (!state.ended) {
  const p = state.pending!;
  const answer = p.kind === 'idle' ? { action: 'end' as const } : p.kind === 'chain' ? { index: -1 } : null;
  state = answer ? (await bridge.respond(answer)).state : (await bridge.advance({ answerFirst: true })).state;
}
bridge.close();
```

Forks for search:

```ts
const fork = await bridge.fork();          // a copy of the duel in a new process
await fork.respond({ action: 'summon', index: 0 });
const board = await fork.snapshot();       // the original duel has not moved
await fork.destroy();
```

## Examples

```bash
(cd client-ts && npm install && npm run build)
node examples/random-duel.mjs 7      # two .ydk deck lists, random legal play
node examples/puzzle.mjs             # a board set up before the duel, win this turn
node examples/puzzle.mjs examples/puzzles/lethal.lua   # the same puzzle as an EDOPro puzzle script
node examples/snapshot-fork.mjs      # try every first action in a fork, keep the best
./build/ocgcore-bridge-extended ...  # examples/extended-server: a query, a filter, a default of its own
```

The examples read `OCGCORE_BRIDGE_BIN`, `OCGCORE_BRIDGE_SCRIPTS` and `OCGCORE_BRIDGE_CDB`
(defaults: `build/ocgcore-bridge` and `tests/data/`).

## Tests

```bash
tests/golden/fetch-data.sh                       # CardScripts + BabelCDB at the pinned commits
cmake -B build && cmake --build build -j
(cd build && ctest --output-on-failure)          # unit, golden and agnostic tests
(cd client-ts && npm install && OCGCORE_BRIDGE_BIN=../build/ocgcore-bridge \
  OCGCORE_BRIDGE_SCRIPTS=../tests/data/CardScripts OCGCORE_BRIDGE_CDB=../tests/data/BabelCDB/cards.cdb npm test)
```

The golden tests play fixed-seed duels over the protocol and compare every step with
`tests/golden/transcripts/`; `node tests/golden/run.mjs ... --update` rewrites them after an
intended change.
